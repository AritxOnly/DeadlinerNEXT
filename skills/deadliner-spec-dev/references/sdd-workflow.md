# SDD Workflow

## 适用场景

- 新功能从 0 到 1 落地
- 大型重构、跨端对齐、breaking change
- 需要先写规格再编码的 Deadliner 工作

## 标准流程

1. 建立 `specs/<feature>/` 目录。
2. 先写 `spec.md`，明确目标、非目标、验收标准和约束。
3. 再写 `module-plan.md`，明确模块边界、分层方式、平台映射和大文件拆分策略。
4. 最后写 `tasks.md`，将实现拆成可验证的阶段。
5. 文档成形后再开始编码。
6. 编码结束后回写规格文档，保证文档描述的是“当前事实”。

## 文档顺序约束

- 不允许先写业务代码、后补规格。
- 若需求还不清晰，先补 `spec.md` 的 open questions，而不是直接实现。
- 若模块划分还摇摆，先冻结 `module-plan.md`，再动代码。

## 规格完成定义

### `spec.md`

- 说清背景、目标、非目标
- 至少列出一个用户场景
- 有可执行的验收标准
- 明确 breaking change 风险与构建约束

### `module-plan.md`

- 至少拆出 2 个逻辑模块
- 标出跨端映射
- 明确哪些文件或组件可能超过 1000 行，需要预防性拆分

### `tasks.md`

- 分阶段推进
- 每个阶段有完成标志
- 说明何时编译、何时只做静态校验

## 开发完成定义

- 规格文档已回写最新状态
- 大文件扫描已执行
- 如果有 breaking change，已有一次全工作区提交作为保护点
- 如果做了大型代码变更，已在最后统一编译验证
